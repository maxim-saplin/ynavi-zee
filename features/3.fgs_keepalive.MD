# Foreground-service keepalive (Android 11 head units)

## What it does

Starts **foreground services** at app launch to keep both the keepalive process and the **main/UI process** alive on devices with aggressive background killing. The keepalive service runs in a dedicated `:persistent` process, while a UI keepalive service runs in the main process so the UI + voice pipeline remain intact in background.

- Services:
  - `ru.yandex.yandexnavi.keepalive.KeepAliveService` (persistent process)
  - `ru.yandex.yandexnavi.keepalive.UiKeepAliveService` (main process)
- Process + FGS type: `android:process=":persistent"`, `foregroundServiceType="location|dataSync"`
- Behavior: posts **ongoing** notifications and returns `START_STICKY`
- Boot + periodic revival:
  - `BootKeepAliveReceiver` starts the service on boot/update.
  - `AlarmManager` reassert loop via `KeepAliveTriggerReceiver` every ~60 seconds.
- Passive location ticks:
  - `LocationManager` (GPS + Network) uses a `PendingIntent` to `KeepAliveTriggerReceiver` to keep the app active even when UI is killed.
- Guidance protection:
  - `GuidanceService` runs in the main process and **requests its own foreground state** via the built-in guidance foreground pipeline to avoid FGS ANR.

## How to configure (build-time)

This feature is controlled via `features/config.env`:

- `ZEEAPP_KEEPALIVE_ENABLED=1` — enable keepalive and apply the mode below.
- `ZEEAPP_KEEPALIVE_ENABLED=0` — disable keepalive entirely (no services declared/started).
- `ZEEAPP_KEEPALIVE_MODE=fgs|audio|off` — pick the strategy when enabled (`fgs` default if missing; `off` skips keepalive even if enabled).
- `ZEEAPP_KEEPALIVE_RECEIVER_EXPORTED_DEBUG=1` — optional ADB/manual triggering of `KeepAliveTriggerReceiver` (exported)
- `ZEEAPP_KEEPALIVE_RECEIVER_EXPORTED_DEBUG=0` — default, receiver stays non-exported

Mode behaviors (applied by `tools/apply_feature_config.py`):
- `fgs`: declares/starts `KeepAliveService` (`:persistent`) and `UiKeepAliveService` (main) with `location|dataSync` FGS types.
- `audio`: declares/starts `AudioKeepAliveService` (`:persistent`, `mediaPlayback`) and also starts `UiKeepAliveService` (main, `location|dataSync`) as a second anchor; MediaSession disabled by default.
- `off`: keepalive blocks omitted even if `ZEEAPP_KEEPALIVE_ENABLED=1`.

Presets: `build_zeekr.sh` → `fgs`, `build_deepal.sh` → `audio`.

Note: Android 8+ requires a notification for foreground services; “keepalive without notification” isn’t supported.

## How to verify (ADB)

- Confirm service exists (after launching the app):

```bash
adb shell dumpsys activity services | grep -n "ru.yandex.yandexnavi/.keepalive.KeepAliveService"
adb shell dumpsys activity services | grep -n "ru.yandex.yandexnavi/.keepalive.UiKeepAliveService"
adb shell dumpsys activity services | grep -n "com.yandex.navikit_platform.guidance.service.GuidanceService"
```

- Confirm notification/channel:

```bash
adb shell dumpsys notification --noredact | grep -n "channel=keepalive"
```

- Confirm `:persistent` process exists (background):

```bash
adb shell ps -A | grep -n "ru.yandex.yandexnavi:persistent"
```

- Confirm passive location registration (should show `KeepAliveTriggerReceiver` requests):

```bash
# Check active location requests for the app
adb shell dumpsys location | sed -n '/Active Location Requests:/,/^$/p' | grep -n "ru.yandex.yandexnavi" || true
```

- Confirm boot + reassert work (Android 11):

```bash
adb reboot && adb wait-for-device && sleep 20
adb shell dumpsys activity services | grep -n "ru.yandex.yandexnavi/.keepalive.KeepAliveService"

# Force-stop then wait ~2 min to see revival
adb shell am force-stop ru.yandex.yandexnavi
sleep 120
adb shell dumpsys activity services | grep -n "ru.yandex.yandexnavi/.keepalive.KeepAliveService"
```

## Notes & Limitations

- UI process can still be killed by the OS when in background; `UiKeepAliveService` exists to reduce this risk and preserve voice guidance.
- Exact alarms: Android 11 allows `setExactAndAllowWhileIdle()`; `SCHEDULE_EXACT_ALARM` is declared for forward compatibility on Android 12+.
- Guidance service entry: `GuidanceService` is not exported; it is started from inside the app when needed, not via ADB.
- Anchor services for notification/accessibility were removed; persistence now relies on the keepalive FGS pair plus the guidance FGS.

- Optional: explicitly test both entry paths:

```bash
# Launcher (icon)
adb shell monkey -p ru.yandex.yandexnavi -c android.intent.category.LAUNCHER 1

# Deep-link
adb shell am start -W -n ru.yandex.yandexnavi/ru.yandex.yandexmaps.launch.LaunchActivity -a android.intent.action.VIEW -c android.intent.category.BROWSABLE -d "yandexnavi://keepalive-test"
```

## Media Mimic (Audio Mode)

The audio-mode strategy mimics lightweight media playback to keep the app alive without hijacking controls. It also starts a second FGS in the main process (`UiKeepAliveService`) to reduce the chance the UI process gets killed while the persistent audio process survives.

- Foreground service: `AudioKeepAliveService` with `foregroundServiceType="mediaPlayback"`.
- Playback signal: a looping `AudioTrack` (PCM16, near-silence) at low volume.
- Media presence: none by default (to avoid media button hijack); optional minimal `MediaSession` if required by a vendor.
- Audio usage: `AudioAttributes` + `AudioFormat` with `USAGE_ASSISTANCE_NAVIGATION_GUIDANCE` / `CONTENT_TYPE_SPEECH` on API 21+ (legacy constructor below that).
- Reassert loop: `AlarmManager` schedules periodic reassert via trigger receiver.
- No controls: avoids transport controls and audio focus so vehicle playback/UI isn’t impacted.

How to verify (ADB):

```bash
# Service present and foreground
adb shell dumpsys activity services | grep -n "ru.yandex.yandexnavi/.keepalive.AudioKeepAliveService"

# Notification/channel exists
adb shell dumpsys notification --noredact | grep -n "channel=keepalive"

# Active media session (only if explicitly enabled)
adb shell cmd media_session list-sessions | cat

# Audio focus remains mostly idle (no long-held focus)
adb shell dumpsys audio | sed -n '/Audio Focus Stack/,/^$/p'

# Optional: observe mixer state
adb shell dumpsys media.audio_flinger | sed -n '1,200p'
```

## Omissions (By Design)

- Audio Focus: not requested to prevent pausing/ducking other playback sources.
- Button Receivers: no media button/transport control receivers registered.
- Anchor Services: no `NotificationListenerService` or `AccessibilityService` declared.
- Forced Routing: no `setPreferredDevice()` or Bluetooth SCO forcing.
- Playback State: unused unless a MediaSession is explicitly enabled; notification stays minimal.

## Future Options (If Required)

- Minimal MediaSession: add a session without transport controls if a vendor requires a session presence.
- Transient Audio Focus: briefly acquire/abandon focus (e.g., `AUDIOFOCUS_GAIN_TRANSIENT_MAY_DUCK`) under a guarded flag.
- AudioAttributes: explicitly set `USAGE_MEDIA` and a stable content type to match OEM heuristics.
- Preferred Device: route the `AudioTrack` to a non-user-visible device via `setPreferredDevice()` where available.
- Notification Tuning: adjust priority/category to maximize survivability without intrusiveness.
- Jittered Reassert: add randomized jitter to alarm intervals to avoid fixed-pattern detection.
- Fallback Path: auto-switch to `fgs` mode if audio is blocked or degraded on target ROMs.

These can be introduced behind build-time flags to keep the default behavior non-invasive while enabling ROM-specific tuning when field testing indicates it’s necessary.
