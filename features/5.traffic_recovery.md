# Traffic Recovery Layer Refresh

This document describes the traffic-recovery behavior in the current working
`src/` tree used for this repo. The recovery path lives inside YNavi smali and
no longer depends on Phase0 automatic restart policy.

The important change is that restored validated connectivity now drives an
in-process traffic-layer refresh, while offline startup is handled by a passive
arming path that does not create an offline relaunch loop.

Tracked baseline note: `a.smali` and `b.smali` are the stable tracked anchor
files in this repo. The current working tree under investigation also wires a
separate callback helper file through `b.smali`; in this checkout that helper is
present as `d.smali`, but its tracked status should be verified before assuming
it exists in another checkout or commit.

## Scope

- recover traffic after connectivity returns without requiring Phase0 automatic restart
- keep the recovery logic inside YNavi's traffic overlay owner
- preserve the active session whenever a layer refresh is sufficient
- cover the offline-start case where YNavi only emits `onTrafficLoading()` before the network becomes healthy

## Current Implementation

### `src/smali_classes5/ru/yandex/yandexmaps/overlays/internal/traffic/a.smali`

This is the `TrafficListener` attached to `TrafficLayer`.

- `onTrafficChanged(non-null)` clears recovery state and dispatches active traffic state
- `onTrafficChanged(null)` dispatches unavailable state and arms recovery
- `onTrafficExpired()` dispatches unavailable state and arms recovery
- `onTrafficLoading()` dispatches loading state and calls the controller's passive arm path
- the file currently logs under the `YNaviTraffic` tag for on-device diagnosis

The key offline-start fix is here: `onTrafficLoading()` no longer triggers an
immediate escalation path. It only gives the controller enough state to wait for
validated connectivity.

### `src/smali_classes5/ru/yandex/yandexmaps/overlays/internal/traffic/b.smali`

This is the traffic recovery controller.

Live recovery path in the current tree:

- `i()` is the active arm path used after `null` traffic or `expired` callbacks
- `p()` is the passive arm path used from `onTrafficLoading()` when traffic is visible, recovery is not already armed, and the active network is missing `INTERNET && VALIDATED`
- `m()` checks the current default network when the traffic layer is made visible
	- if validated connectivity is already present and recovery is armed, it immediately refreshes the layer
	- otherwise it registers a default network callback
- `o()` handles a validated network callback and refreshes only when recovery is armed and traffic is visible
- `q()` performs the in-process refresh that is actually used now:
	- remove the traffic listener
	- set traffic visibility `false`
	- set traffic visibility `true`
	- reattach the traffic listener
- `h()` clears armed state, disposes any scheduled retry disposable, and unregisters the network callback

This means the current source tree is centered on a traffic-layer refresh rather
than on a host recreation or external app restart.

Notes about leftover methods:

- the class still contains older retry/restart-era helpers such as `k()` and `l()`
- `l()` still calls the internal restart helper in `ru.yandex.yandexmaps.app.m`
- the documented live callback path above goes through `q()`; the restart helper is not the primary behavior described by the current smali listener/callback flow

### Network Callback Ownership

The current working tree keeps callback ownership in `b.smali` and currently
instantiates `d.smali` as the concrete helper:

- `k` stores the controller's current `ConnectivityManager.NetworkCallback`
- `m()` and `p()` register the default callback when the controller needs to wait
- `h()` unregisters that callback during recovery teardown
- `m()` and `p()` currently construct `new d(this)` before registering it

For maintenance, treat `a.smali` and `b.smali` as the first diff targets, then
check whether the callback helper file present in your checkout is tracked or
local-only before promoting it into long-term repo documentation.

## Why This Replaced The Older Doc

The earlier writeup in this file described a delayed host-reset /
`Activity.recreate()` design. The current `src/` tree no longer matches that
description:

- `onTrafficLoading()` now participates in recovery arming
- the documented live refresh path is the `q()` traffic-layer refresh
- the code carries `YNaviTraffic` instrumentation added during the on-car diagnosis cycle

This file is therefore the source-of-truth description of the current tree, not
of the older accepted branch from earlier emulator validation.

## Validation Context

The current controller shape was produced by the on-car debugging branch that
proved two things:

- validated connectivity callbacks were reaching YNavi after restore
- the offline-start failure could still be ignored if recovery was never armed

The passive loading-arm path closes that gap without reintroducing the rejected
offline relaunch loop.

## Maintenance Note

If traffic recovery regresses again, diff `a.smali` and `b.smali` first, then
inspect the callback helper currently instantiated from `b.smali` in your
checkout. Do not reintroduce Phase0 automatic restart as the default solution
without proving that the YNavi-side layer refresh path is insufficient.
